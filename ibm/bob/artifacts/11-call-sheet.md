## Plan

Render something a first AD would recognise. The judges include people who have
held a real call sheet, and a fake one is obvious at a glance.

## What the PDF contains

Header with production title, day N of M, date, weather, sunrise and sunset.
Crew call, first shot and estimated wrap as three large figures. A location
block with address, parking and nearest hospital. The scenes table — number,
INT/EXT, D/N, description, pages in eighths, cast ids, minutes. A cast table
with pickup, call and on-set times. The equipment list. And a footer:

```
Generated by PRI — state version 2 — a3f1c9e02b41
```

## Decisions

**Logistics live in config, not in `ProductionState`.** A hospital address
cannot make a schedule illegal, so versioning it would add churn to the state
chain for nothing. `config/logistics.yaml` is looked up at render time.

**A missing logistics file degrades to em-dashes rather than failing.** A call
sheet without a parking note is still a call sheet, and V6 only asks that one
exists — failing the execution pipeline over a missing YAML would be the wrong
trade.

**The footer carries the version and digest.** A sheet found on a table traces
back to exactly the state that produced it. This is the cheapest possible
provenance and it costs one line.

**Pages rendered in eighths.** One minute per eighth is the standard rough
equivalence, so a 210-minute scene reads as `26 2/8`. A crew member scanning the
sheet expects that column to look like that.

**`generate_call_sheet_delta` marks rows `CHANGED`.** "Changed" means the scene
was not on this day before, or its position moved — what a crew member needs is
"these lines are new to *your* day", not a diff of the whole production.

## Wiring

Called by `TransitionService` step 6 via `regenerate_all(state)`. Written to
`artifacts/call_sheets/{production}/v{version}/{date}.pdf` and registered in the
`artifacts` table, which is what verification check V6 looks for. Days with no
scenes are skipped — a reserve day nobody is called to does not need a sheet.

## How to run it

```python
from datetime import date
from pri.persistence.seed import build_state
from pri.artifacts.call_sheet import generate_call_sheet

pdf = generate_call_sheet(build_state(), date(2026, 9, 10))
# 3,578 bytes, starts with b'%PDF-'
```

Downloadable from the running API at `/api/artifacts/{artifact_id}`.

## Not covered

**No test file.** The module is exercised end to end by
`tests/api/test_wow_scenario.py::test_call_sheet_downloads_as_a_pdf` and by the
transition suite, both of which assert the bytes start with `%PDF-` and that the
artifact is registered — but nothing asserts the *content* of the rendered page.
A rendered-text assertion would catch a layout regression that the current tests
would miss entirely.

**Weather, sunrise and sunset are constants.** They come from
`config/logistics.yaml` defaults and are the same on every sheet. A real call
sheet gets these per-date from a forecast.

**Storage is container-local.** Cloud Run's filesystem is ephemeral. The
artifact table records the path and a regenerated version rewrites it, so
nothing durable is lost — but a link to a previous version's sheet will 410 after
a restart. A GCS bucket is about twenty lines.
