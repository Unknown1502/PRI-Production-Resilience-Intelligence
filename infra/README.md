# Deploying PRI to Cloud Run

Three services and one job. The whole thing is one script, but read this first —
there are two values you have to set by hand and one ongoing charge you should
know about before you create it.

## What gets created

| Resource | What it is | Scaling |
|---|---|---|
| `pri-api` | FastAPI — engine, SSE stream, artifacts | min 0, max 4, concurrency 40 |
| `pri-web` | Next.js console | min 0, max 4, concurrency 80 |
| `pri-consumer` | Confluent listener | **min 1**, max 1 |
| `pri-seed` | One-shot job: migrations + demo fixture | run on demand |
| `pri-db` | Cloud SQL Postgres 16, `db-f1-micro` | — |

### The cost note

**`pri-consumer` at min-instances 1 is the only always-on charge.** Everything
else scales to zero between visits, which is what you want for a judged demo
that gets opened a handful of times over two weeks. The consumer cannot scale
to zero and still be a consumer: a Kafka listener with no instance running is
not listening, and the disruption that arrives while it is asleep is exactly the
one the system exists to catch.

Roughly, at the time of writing: one always-on `cpu=1, memory=512Mi` Cloud Run
instance plus a `db-f1-micro` Cloud SQL instance. If you need to cut it to zero
after judging, `gcloud run services update pri-consumer --min-instances 0` — the
API path still works, you just lose the Kafka trigger.

## Before you run it

```bash
export GOOGLE_CLOUD_PROJECT=your-project-id
export GOOGLE_CLOUD_LOCATION=us-central1

# From the Confluent Cloud console. The script refuses to run without these —
# a partial deploy leaves a URL that half works, which is the hardest thing to
# debug under time pressure.
export CONFLUENT_BOOTSTRAP_SERVERS=pkc-xxxxx.us-east-1.aws.confluent.cloud:9092
export CONFLUENT_API_KEY=...
export CONFLUENT_API_SECRET=...

# Guards the API's mutating routes. The browser never sees it: the web service
# holds it and its /api/pri proxy adds it server-side.
export PRI_API_KEY=...

# Do NOT set GOOGLE_APPLICATION_CREDENTIALS. Cloud Run's service account
# supplies credentials, and a path that does not resolve makes the Google auth
# library raise rather than fall back.

# Leave empty to let a judge drive the console with no credentials.
export PRI_API_KEY=
```

The database password is **generated by the script** and written straight to
Secret Manager. It is never printed and never passed on a command line. If you
need it later, read it back:

```bash
gcloud secrets versions access latest --secret=pri-db-password
```

## Run it

```bash
./infra/deploy.sh
```

Ordered, and idempotent at every step — re-run it after a partial failure and it
picks up where it stopped rather than erroring on resources that already exist.

1. Enable `run`, `sqladmin`, `secretmanager`, `artifactregistry`, `cloudbuild`, `aiplatform`
2. Create the Artifact Registry repo
3. Create Cloud SQL, the database, and the user with a generated password
4. Put the DB password and Confluent credentials into Secret Manager
5. Build and push `api` and `consumer`
6. Deploy `pri-api` with the Cloud SQL socket attached
7. Run `pri-seed` — migrations, then the demo fixture at version 1
8. Deploy `pri-consumer` pointed at the API's internal URL
9. Build and deploy `web`. No build arguments: the browser only ever calls the
   web service's own `/api/pri` proxy, which reads `PRI_API_BASE_URL` and
   `PRI_API_KEY` from the environment at request time. One image works against
   any backend URL, and no credential reaches the browser.

## Verify

`infra/verify.sh` checks the whole pipeline, not just liveness, and writes its
output to `docs/evidence/runtime/`. This is the script to run after a deploy and
on the judging dates.

```bash
API="$(gcloud run services describe pri-api --region us-central1 --format='value(status.url)')"
PRI_API_KEY=... ./infra/verify.sh "$API"
```

It exits non-zero if anything fails, and checks: `/health` returns 200 with the
database ok, the overview returns a production, a disruption produces candidates
including one the validator rejected, the demo reset succeeds, and a call sheet
downloads with an intact PDF header.

### The go/no-go gate

`verify.sh` proves the pipeline works for one caller. It does not prove it works
for two at once, which is the thing the deployment is actually pinned for. Run
this last, immediately before the judging window:

```bash
WEB="$(gcloud run services describe pri-web --region us-central1 --format='value(status.url)')"
PRI_API_KEY=... python scripts/verify_live_demo.py "$WEB"
```

It opens two independent SSE connections, drives one disruption through ingest,
recovery, approval and execution, and asserts that *both* connections saw all
ten pipeline stages in the right order — then fetches the resulting call sheet
on a third connection that shares nothing with either. Two viewers seeing
different streams means `pri-api` is serving more than one instance and the
in-process broker has split; the failure message says so.

It takes either the web URL or the API URL. It resets to version 1 at the start,
because the invalid-candidate stages need a clean board, and again at the end,
because it commits a version and the demo has to start clean. Exit 0 prints
`GO`; anything else prints `NO-GO` and names the assertion that broke.

`kafka: degraded` is a pass. PRI works without the event fabric by design, and
only a database failure returns 503 — a `/health` that 503s on a broker problem
would make Cloud Run cycle an instance that is serving perfectly well.

`/health` runs a real `SELECT 1`, not a connection-pool glance — Cloud Run will
happily route traffic to an instance whose Cloud SQL socket has gone away, and a
health check that cannot detect that is decoration.

```json
{"status":"ok","version":"0.1.0","git_sha":"a1b2c3d","database":"up","agent_enabled":true}
```

Then drive the whole story:

```bash
python scripts/run_demo.py --api https://pri-api-xxxxx.run.app
```

## Cold starts

`pri-api` scales to zero, so the first request after a quiet period waits for a
container. Two things absorb it:

- The web console renders the overview from a cached snapshot rather than a
  spinner, so a judge opening the URL sees the production immediately.
- `scripts/run_demo.py` calls `/health` first, which wakes the instance before
  anything that matters is timed.

## Redeploying one service

```bash
GIT_SHA=$(git rev-parse --short HEAD)
gcloud builds submit --tag "$REGION-docker.pkg.dev/$PROJECT/pri/api:$GIT_SHA" --file Dockerfile.api .
gcloud run deploy pri-api --image "$REGION-docker.pkg.dev/$PROJECT/pri/api:$GIT_SHA" --region "$REGION"
```

## Tearing it down

```bash
gcloud run services delete pri-api pri-web pri-consumer --region us-central1
gcloud run jobs delete pri-seed --region us-central1
gcloud sql instances delete pri-db
gcloud artifacts repositories delete pri --location us-central1
```

Secret Manager entries survive on purpose — deleting a database password
alongside the database is how you discover you needed a backup.
